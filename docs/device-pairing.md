# 设备配对（1.0.1）

新设备不需要 `.kpkey` 文件：经另一台已开启云同步的设备核对确认码并批准后，自动取得数据密钥。服务器只中转，看不到任何能解开保险库的东西。`.kpkey` 退为应急恢复：手边没有任何已同步设备时才用。

## 什么时候会用到

| 场景 | 流程 |
| --- | --- |
| 新电脑，创建保险库时选「从另一台设备同步（换电脑）」 | 设置短密钥 → 自动打开 设置 → 云同步 → 填邮箱、网站密码、验证码绑定 → 弹出「从其他设备获取密钥」→ 在老电脑上批准 → 云端数据下载 |
| 本机已有数据，第一次开启同步，云端已有别的设备上传的数据 | 绑定后同样弹出配对窗口；取得云端密钥后合并：没有冲突直接上传，有冲突逐条选择保留本机还是云端 |
| 本机已有数据，云端为空 | 和以前一样，直接用本机密钥上传，不需要配对 |
| 云端换过密钥，本机同步暂停 | 云同步卡片里点「从其他设备获取密钥…」（也可以「用密钥文件恢复同步…」） |

## 协议

1. 新设备 N 生成临时 X25519 密钥对，只提交公钥承诺 `sha256("keep-password/pair-commit/v1" ‖ N公钥)`。
2. 已绑定的设备 O 每 10 秒检查一次待批准请求，自动用自己的临时公钥响应（只有本机密钥就是云端密钥时才响应）。
3. N 拿到 O 的公钥后才公开自己的公钥；O 核对承诺。两边用 `HKDF(N公钥‖O公钥)` 算出同一个 6 位确认码。
4. 用户核对两边确认码一致，在 O 上点「批准」。O 用 ECDH + HKDF 派生的 AES-256-GCM 密钥加密数据密钥，经服务器转给 N。
5. N 上也要点「两边一致，继续」才接收密钥，然后走与选择密钥文件完全相同的校验与合并，最后通知服务器清空会话。

为什么要这样：

- **先承诺、后公开**：服务器冒充任一方，都必须在不知道对方公钥时先选定自己的密钥，挑不出让两边确认码相同的密钥（成功率百万分之一）。
- **新设备也要确认**：否则恶意服务器可以冒充“老设备”塞一把假密钥，让新设备把本地数据用假密钥加密上传。
- 模式写进 AES-GCM 的附加数据，改动模式字段就解不开。

## 二维码（为移动端准备）

新设备的等待窗口同时显示二维码，内容为 `kppair1:` + base64url(JSON{配对编号, N公钥, 32 字节一次性秘密})，不含数据密钥。扫码方调用 `PairingApproval.ApproveScannedAsync`：核对二维码公钥与服务器上的承诺，响应并直接批准，一次性秘密参与密钥派生。服务器没见过这段秘密，伪造不出解得开的信封，所以 N 解开扫码信封即视为已认证，不需要再点确认。桌面端目前只显示二维码，扫码批准留给以后的手机端。

## 服务端

`/api/sync/pairing`、`/pending`、`/:id`、`/:id/offer|reveal|approve|reject|complete`，见服务端 README。10 分钟过期，完成后清空公钥和信封，每账号 10 分钟最多 10 次。
